## 8. 在线更新

### 做了什么

- `features/updater.js`：
  - 清单优先 GitHub Contents API（内容实时），失败回退 raw / jsdelivr / ghproxy；
  - 下载用 Electron `net.fetch`（走系统代理），支持镜像回退；
  - 流式写入 + 进度回调 + SHA-256 校验；
  - 安装：退出主程序 → PowerShell 静默 `/S` → 若 exe 未写回自动再跑一次 → 自动重启。
- `updates.json`：版本、minVersion、下载地址、镜像、SHA-256、更新日志条目、插件列表、目录版本。
- 设置页「检查更新」+ 启动 5 秒静默检查；发现新版弹日志 → 手动下载 → 进度 → 自动安装。
- 发布 v1.1.0、v1.1.1（NSIS + APK）。

### 实测结果

- 清单：`latest 1.1.1`，URL 正确。
- 下载：141,296,372 字节（135 MB），进度 100%。
- SHA-256 与发布值一致：`2749dd72…eed9b`（1.1.0）；1.1.1 为 `2cacdb83…bad6d`。
- v1.1.1 已覆盖安装，当前运行 1.1.1。

### 踩坑与修复

- GitHub raw CDN 缓存滞后，清单读到旧 URL → 改用 Contents API。
- `gh release create` 会把含中文/空格的安装包名改成 `Setup.1.1.0.exe` → 发布时使用 ASCII 副本 `nailong-Setup-1.1.1.exe`。
- NSIS 原地覆盖偶发「主 exe 消失」→ 安装脚本检测不到 exe 时自动再跑一次。
- 直连 GitHub 不稳定 → 清单/下载均支持镜像，推送用系统代理。

## 35. 自动更新闭环（2.0.1）

- 旧脚本的问题：装完只在 `%LOCALAPPDATA%\Programs\nailong` 找 exe 重启，而本机装在 `D:\nailong-app`，所以更新后不会自动回来；也没有周期检查（只在聊天窗口加载 5 秒后查一次）。
- `applyUpdate`：PowerShell 先等旧进程退出，再 `/S /D=<当前安装目录>` 原地静默安装（NSIS 的 /D= 不能加引号，路径带空格就退回默认目录），失败自动按默认目录再装一次；装完修正桌面快捷方式并启动新 exe。
- `startUpdateWatcher`：启动 8 秒后查一次、此后每 6 小时一次；聊天窗开着发通知，否则用桌宠气泡（受气泡开关控制）。
- 进化动画只在 `app.getVersion().startsWith(data/evolution.json.version)` 时播放，2.0.1 这类补丁版不再重播 2.0 的动画。
- 自检：`--update-install <exe>`、`--apply-update`（检查→下载→安装→重启全链路）。

### 35.1 更正：PowerShell 不可用，改 cmd（2026-10-22 实测）

- 实测一：GUI 进程（无控制台）里 `spawn('powershell', …, {detached:true, stdio:'ignore'})` 启动的 PowerShell **立即退出、脚本一行都不执行**；`detached-pipes` 同样不行。这就是 1.18.1 用户点更新后「奶龙关掉了、再也没回来」的根因。
- 实测二：Electron 退出时，同 job 的子进程会被一起带走（Chromium job object；harness 里更明显）。
- 结论：更新器改为纯 `cmd.exe`：`install-update.cmd`（ASCII，路径全走 `NAILONG_*` 环境变量）→ `ping` 等待旧进程退出 → `start /wait` 静默 `/S /D=<安装目录>`（NSIS 是 GUI 程序，不加 `/wait` 不会等）→ 失败按默认目录再来一次 → `wscript` 重建桌面快捷方式 → `start` 启动新版。
- 实测三：`start /wait "" installer /S /D=…` 原地安装 exit=0（约 45–75 秒），随后 `running=4`（新版自动启动），`install.log` 有 start/exit 两行。
- 实测四：静默安装会把桌面快捷方式删掉且不重建；补 `ensureDesktopShortcut()`（wscript + VBS，启动时自愈），删掉 .lnk 后启动奶龙，1 秒内图标恢复且指向 `D:\nailong-app\奶龙.exe`。
- 自检命令不变：`--update-install <exe>`、`--apply-update`；日志在 `%TEMP%\nailong-update\install.log`。

## 40. 解题卡真正的根因：推理吃掉了输出预算（2.2.2）

- 失败时留下的原始输出是一大段「我们需要回答用户…」的推理过程（26KB），不是 JSON。
- 根因：结构化请求没有关闭推理，推理把 8000 token 的输出预算吃光，`content` 为空；2.2.1 又把 `reasoning_content` 当正文去解析，于是必然「JSON 解析失败」。
- 修复：
  1. 新增 `ai.askJsonRaw`：结构化请求默认带 `reasoning_effort: "none"`（探针实测 `content` 直接是 JSON、`reasoning` 长度 0）；供应商不认该字段时自动退回普通 JSON 请求。
  2. `solve` 改为：先解析正文/推理里的 JSON；若只有思考过程，走**二次压缩**——用短系统提示词「只做 JSON 格式化」，把过程整理成解题卡（不重新解题）。
  3. 失败时同时写 `.txt` 原始输出和 `.meta.txt` 失败原因。
- 实测：电磁感应导轨三问（9s）、斜面+电容三问、OCR 残缺题干（107s）全部生成成功；`--explaintest` 对硬题完整走到渲染讲解页。
- 新增自检：`--jsonprobe`、`--explaintest "<题目>"`。
